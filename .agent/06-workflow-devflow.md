# 分册 6｜开发全流程

> 归属总纲：`../1-总纲/AGENT.md`
> 覆盖：需求 → 方案 → 分支 → 生成 → 编码 → 自测 → 提交 → PR → 联调 → 验收 → 发布 → 复盘

---

## 0. 全流程总览

```
   需求    ──▶ 技术方案 ──▶ 建分支 ──▶ 代码生成 ──▶ 业务编码
      │                                                   │
      │                                                   ▼
  发布复盘 ◀── 线上观察 ◀── 发布/回滚 ◀── 验收 ◀── 自测(4步跑通)
                                            ▲
                                       联调/评审(PR)
```

---

## 1. 阶段一：需求澄清（输入：需求文档）

| 项 | 要求 |
|----|------|
| 输入 | 需求/Bug 描述、原型或接口约定（**不需要工单编号**） |
| 产出 | 需求理解确认清单（字段、状态枚举、边界、权限） |
| 红线 | 不编造需求外的功能；需求描述不清必须确认后再开工 |

确认清单模板：
- 涉及哪些表/字段？是否需要 DDL（**需单独确认，禁止直接执行**）？
- 状态枚举与流转？是否涉及 Kafka 事件？是否涉及外部服务调用（HTTP/gRPC）？
- 权限口径（谁能看、谁能写）？是否需要操作日志？
- 前端页面与字段展示口径？

---

## 2. 阶段二：技术方案（输出：方案 + 变更清单）

1. 表结构变更方案（SQL 脚本 + 回滚脚本，放 `sql/`）。
2. 接口清单（方法、路径、入参、出参、错误码）。
3. 分层落点：`model/`、`request/response/`、`service`、`api`、`router` 各改哪些文件。
4. 是否可用代码生成器（能生成的一律生成）。
5. 外部依赖：外部服务接口（HTTP/gRPC）、Kafka topic、pgvector 检索。
6. 输出【变更文件清单】并请负责人确认（涉表/涉框架必须 Ask）。

---

## 3. 阶段三：分支与环境

```bash
git switch main && git pull
git switch -c feature/xxx      # 或 fix/ opt/ hotfix/ docs/ test/
```

- 业务代码**禁止直推 `main`**；框架类改动单独分支、单独 PR。
- 本地环境：`config.dev.yaml`；依赖服务（PostgreSQL、Redis、Kafka）就绪。

---

## 4. 阶段四：代码生成 + 业务编码

1. **先生成**：用 GVA 代码生成器产出 CRUD 骨架（model / request / response / api / service / router）。
2. **再补齐**：
   - `model`：字段与 DDL 对齐，可嵌入 `global.GVA_MODEL`（仅复用 ID/CreatedAt/UpdatedAt/DeletedAt，不绑定连接），CRUD 由 `global.LUOBO_DB` 发起。
   - `request`：Search / CreateReq / UpdateReq，单号类字段不出现在入参。
   - `service`：业务逻辑、事务、单号生成（`global.Snow`）、外部服务调用、Kafka 收发、向量检索。
   - `api`：参数校验规则（写在模块 `enter.go`）、swagger 注释、统一返回。
   - `router`：写操作挂 `middleware.OperationRecord()`。
   - `enter.go` ×3 + `initialize/router_biz.go` 注册。
3. 遵循分册 3 全部规范；不随手扩大改动面。

---

## 5. 阶段五：自测（四步跑通，见分册 5）

| 步骤 | 内容 | 产物 |
|------|------|------|
| 1 | 构建：`go build ./...` 无 error（`go vet` 报错必修） | 终端输出 |
| 2 | 启动：服务能起来，日志无 panic | 启动日志 |
| 3 | 接口：Apipost 正常用例 `code=0` + 一个失败用例有正确提示 | 请求/响应截图 |
| 4 | 页面：能打开、Console 无 Error、主流程点得通 | 页面截图 |

**开发初期只要四步各跑通一次即可交付**；哪一步出问题就修哪一步再重跑该步。进入联调/上线前按分册 5 §6 恢复完整回归口径。

---

## 6. 阶段六：提交与 PR

```bash
git status                      # 确认无夹带
git add <明确文件>               # 禁止 git add .
git commit -m "[feat] [v2.1.0] 新增客服工单模块"
git push origin feature/xxx
```

- 一个 commit 一个类型；混合变更拆分提交（见分册 4）。
- 冲突按分册 4 第 4 节处理，解决后重新构建 + 自测。
- PR 按模板填写：变更类型、变更文件清单、实现说明、自测情况、影响面与回滚（**无「关联编号」模块**）。

---

## 7. 阶段七：评审与联调

- 代码评审：分层是否规范、是否有 SQL 拼接、是否有敏感信息、是否有越权、测试是否充分。
- 与前端联调：字段口径一致（驼峰命名）、错误码与提示一致、分页字段一致。
- 与外部服务联调：接口契约（HTTP/gRPC）一致，超时/重试/降级策略明确。
- 评审不通过 → 回到阶段四，修复后重新走完整自测。

---

## 8. 阶段八：发布与回滚

1. 发布前：DB 脚本先评审、先备份、灰度/低峰执行；配置项与密钥通过环境变量注入。
2. 发布顺序：DB 脚本 → 后端服务 → 前端资源。
3. 发布后观察：错误日志、接口成功率、Kafka 消费延迟、PG 慢查询。
4. 回滚预案：服务回滚版本、SQL 回滚脚本、Kafka 补偿方案，**每次发布必须在 PR 中写明**。

---

## 9. 阶段九：复盘与归档

- 更新接口文档（swagger）与需求状态（**不涉及工单编号**）。
- 复盘记录：问题、根因、改进项（走 `opt` 类型 commit/分支）。
- 文档变更走 `[docs]`，测试补充走 `[test]`。

---

## 10. 各阶段 DoD 速查

| 阶段 | DoD |
|------|-----|
| 需求 | 有确认清单、无二义性 |
| 方案 | 有接口清单、变更文件清单、DDL 已确认未执行 |
| 编码 | 生成器产出骨架 + 业务层补齐，未改框架底盘 |
| 自测 | 构建/启动/接口/页面四步跑通，结果已说明 |
| 提交 | 格式合规、一次一事、无夹带、冲突已解决并重测 |
| PR | 模板齐全、评审通过、回滚方案明确 |
| 发布 | 脚本评审通过、观察指标正常、回滚预案就绪 |
| 复盘 | 文档更新、改进项有归属有负责人 |
